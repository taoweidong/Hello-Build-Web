## 一、原始需求文档要点提取（业务原始背景.md）

### 1.1 业务领域（三环节交付链路）

| 环节 | 职责 |
|---|---|
| 构建 | 下载软件代码，编译产出二进制（供防护网验证） |
| 防护网 | 测试二进制的业务功能是否正确（冒烟 + 人工分析） |
| 集成 | 接收构建推送的代码，集成并发布版本 |

### 1.2 使用角色（原始 4 类，设计阶段扩为 5 类）

- 构建人员
- 防护网测试人员
- 集成人员
- 项目经理 PM

> 设计基线补充了「系统管理员」，共 5 类角色。

### 1.3 关键操作定义

| 操作 | 含义 | 耗时（原始值） |
|---|---|---|
| 代码构建 | 下载代码做二进制编译 | 30min |
| 冒烟 | 真实环境加载二进制并执行测试用例 | 8H / 2H / 1H（随场景） |
| 人工分析 | 对用例执行结果人工分析并给出结论 | 2H / 1H / 0.5H（随场景） |
| 推送 | 将软件仓库代码推送集成仓库 | 20min |
| 构建策略 | 不同流程场景即为一种构建策略 | — |

### 1.4 三个标准流程场景（每日循环）

| 场景 | 构建时间 | 冒烟耗时 | 人工分析 | 推送 |
|---|---|---|---|---|
| 场景1（晚间全量） | 每晚定时 | 8H | 2H | 20min |
| 场景2（午间快速） | 每天中午 | 2H | 1H | 20min |
| 场景3（16:30 定点） | 每天下午 16:30 | 1H | 0.5H | 20min |

统一节奏：**定时构建 → 构建完自动吊起冒烟 → 冒烟完人工分析出结论 → 根据结论推送集成**。

### 1.5 版本与分支维度

- 版本命名：27A、27B、26B 等（不同版本 = 不同项目周期）；
- 分支命名：master、TR5、TR6 等（同一版本下多分支）；
- 不同版本/分支对应**不同的构建策略组合**。

### 1.6 原始目标（原文提炼）

1. 设计一个 **Web 系统**，由 PM 配置**不同版本、不同分支**的构建策略；
2. 构建策略 = 配置**构建、冒烟、推送**等关键流程的时间节点，由这些节点串起完整流程；
3. **权限约束**：不同版本的 PM 不同，本版本 PM 只能配置本版本的构建策略；
4. **默认耗时规则**：冒烟后有默认 8H/2H 系统测试时间，随后默认 2H 人工分析，分析完毕后按结论推送。

### 1.7 原始技术要求

- 仅一条硬性约束：**技术栈使用 Vue3**。
- 后端技术栈原始需求未指定（FastAPI 是设计阶段选型，后于 2026-08-10 迁移至 Django）。

## 二、业务现状与系统定位（2026-10-11 业务背景补充）

### 2.1 现有定时调度机制

- **配置存储**：Git 仓库 `Jenkins_smart_ci_xml`，负责存储定时调度相关的 **XML 配置信息**；
- **调度系统**：XML 配置供 **JenkinSmartCI 系统**使用——只要 Git 仓库中的 XML 发生变化，系统即可感知并调整调度，由它负责**定时调度任务**；
- **调度内容**：被调度的任务包含**构建工程、调起冒烟**等（即原始需求中「构建 → 冒烟 → 分析 → 推送」各环节的实际执行载体）。

链路示意：

```
XML 配置（Jenkins_smart_ci_xml 仓库）
        │  上库（push 变更）
        ▼
JenkinSmartCI 感知变化 ──► 按新配置定时调度任务（构建工程 / 调起冒烟 等）
```

### 2.2 原业务流程与痛点

原流程：**人工修改 XML → 上库 → JenkinSmartCI 自动感知 → 定时调度**。

痛点：
1. 修改全靠人工编辑 XML 并上库，易错、效率低、无权限与变更记录控制；
2. **无法观察全部定时调度情况**——全局调度全景不可视，各版本/分支任务交织后难以掌握。

### 2.3 当前系统的目标定位（补充后）

构建一个 Web 系统：
1. **可视化修改定时调度及其参数**（时间、触发属性等），替代人工改 XML；
2. 修改后**自动调用 Git 接口完成修改上库**——只要变更推送到 Git 仓库，JenkinSmartCI 即可感知并按新配置调度，系统本身不直接驱动构建；
3. 提供**可视化页面观察调度任务全景**，补齐「看不见全局调度」的短板。

### 2.4 核心目标细化（三大核心目标）

| # | 目标 | 面向角色 | 内容要点 | 修改权限 |
|---|---|---|---|---|
| 1 | **可视化修改 XML** | 调度配置者 | XML 中需要修改的内容不多，**主要是时间**和**部分参数**；**其他任务配置不在此处修改** | 受限写入：只改约定字段，且**可视化修改不能影响其他功能**（XML 其余部分必须原样保留） |
| 2 | **调度全景（对外）** | 项目经理、用户（对外人员） | 一个页面呈现**整体版本调度情况**，供查看全局 | 以只读查看为主，**支持部分时间的延迟类修改**（受限调整） |
| 3 | **调度全景（对内）** | 构建、测试人员（对内人员） | 一个页面展示调度详情，面向执行角色 | **支持修改，支持各种定制化修改**（更强的编辑能力） |

工程含义提示（分析结论，非原始文字）：
- 目标 1 决定了 XML 写入必须是**精确的局部字段修改**（按属性定位改值），不能整文件重写，否则会破坏目标 1 的「不影响其他功能」约束；
- 目标 2/3 实为**同一全景数据的两套视图**：对外只读 + 受限改时间，对内可编辑 + 定制化——与设计基线「页面 × 角色权限矩阵」的按角色裁剪思路一致，可映射为甘特/全景页的角色化读写能力。

### 2.5 与原始需求的关系

本节是对 `业务原始背景.md` 的落地背景补充：原始需求中「构建策略 = 配置构建/冒烟等时间节点」的**物理载体正是 XML 配置 + JenkinSmartCI 调度体系**。本 Web 系统的本质定位：为这套既有机制加上一层「**可视化配置 + Git 自动上库 + 调度全景可视化**」——系统是配置与观察的入口，真正的执行仍由 JenkinSmartCI 完成（对应设计基线中「本期只做配置+展示、外部动作走适配器」的边界决策）。

## 三、需求基线补充的 19 项关键决策（2026-08-08 确认）

原始需求较粗，正式设计时逐项澄清，关键结论：

### 3.1 系统边界

- **本期只做「配置 + 展示」**：不实现真实构建/防护网/集成驱动，外部动作（推送、通知）走 mock 适配器留痕；
- 架构预留端口抽象层（PushPort / NotifyPort / AuthProviderPort / SchedulerPort），演进为流程编排中枢。

### 3.2 核心模型

- **一条策略 = 模板（固定阶段耗时）+ 构建开始时间（HH:MM 每日循环）+ 推送模式 + 启用状态**；
- PM 只配两个节点：构建开始时间 + 推送模式；冒烟/人工分析耗时由模板决定，PM 不可改；
- **配置（strategy）与执行实例（execution_round）分离**：每日执行按当日快照跑，支撑「变更次日生效、当日不受影响」。

### 3.3 两种推送模式

| 模式 | 推送时机 | 结论的作用 |
|---|---|---|
| 同步推送冒烟 | 构建**前**推送（推送须在构建开始前 20min 完成） | 仅评估是否正式发布 |
| 正常流程推送 | 结论**通过后**自动推送 | 控制是否推送集成 + 是否发布；不通过则本轮终止 |

### 3.4 冲突与生效规则

- 冲突检测**仅限同分支**：时间区间不得交错，冲突**阻止保存**（错误码 40901，前端有专用弹框）；
- 检测窗口 48h（防跨天交错）；
- 变更生效：当日未开始 → 当日生效；已开始 → 本轮按旧配置，次日起生效；
- 每次修改写策略变更日志（谁/何时/改了什么）。

### 3.5 权限模型

- PM ↔ 版本**一对一**（`version.pm_user_id` UNIQUE）；
- PM 可查看全局版本计划（只读），仅能写本版本策略；
- 管理员独占系统管理（版本/分支/用户/模板/全局配置）；
- 防护网测试人员独占「录入结论」操作。

### 3.6 数据与日志

- 核心表 7 张：user / version / branch / strategy_template / strategy / execution_round / global_config；
- 日志 4 类：执行日志、策略变更日志、管理操作日志、登录安全日志；
- 版本/分支/策略**软删除**，保护历史日志；
- 结论双字段：conclusion（正常模式）+ release_approved（同步模式）。

## 五、关键信息速查卡

- **一句话现状**：定时调度配置以 XML 形式存放在 `Jenkins_smart_ci_xml` Git 仓库，由 JenkinSmartCI 感知变更并调度构建/冒烟任务；目前靠人工改 XML 上库，且看不到全局调度全景。
- **一句话需求**：一个让 PM 按「版本 → 分支」配置每日构建策略（构建/冒烟/分析/推送时间节点）的 Web 系统，可视化改调度参数后自动经 Git 接口上库（JenkinSmartCI 感知生效），并带全角色调度全景可视化与冲突防护。
- **流程主干**：定时构建(30min) → 冒烟(8H/2H/1H) → 人工分析(2H/1H/0.5H) → 结论 → 推送集成(20min)。
- **三大核心目标**：① 可视化改 XML（仅时间+部分参数，不动其他配置、不影响其他功能）；② 对外调度全景（PM/用户，只读为主+部分延迟时间调整）；③ 对内调度全景（构建/测试人员，可编辑+定制化修改）。
- **最重要的三条业务规则**：
  1. PM 与版本一对一，只能改本版本策略；
  2. 同分支策略时间区间不得交错，冲突阻止保存；
  3. 策略变更次日生效，当日执行轮次按旧配置快照。
- **不可破坏的既有约定**：统一响应 `{code, message, data}`、错误码语义固定（尤其 40901 专用策略冲突）、策略写路径统一走 services 层、展示映射唯一来源 `src/views/constants.ts`。
